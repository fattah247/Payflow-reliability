# 012 Schema Migrations with Flyway

## Context

The schema was generated by Hibernate (`ddl-auto: update`). That cannot express check constraints or composite uniqueness reliably, silently alters schemas, and cannot drop or rename anything. The concurrency guarantees in ADR 009 depend on constraints the database must enforce.

## Decision

Flyway owns the schema (`src/main/resources/db/migration`). Hibernate runs in `validate` mode and refuses to start if entities and schema disagree. The same migrations run on H2 (tests) and PostgreSQL (runtime and CI).

## Tradeoffs

Schema changes now need a migration file. Local databases created by the old Hibernate-managed schema must be reset once (`docker compose down -v`), because Flyway refuses to adopt a non-empty schema without history.

## Consequences

The schema is reviewable in one file, invariants live next to the data, and entity/schema drift fails fast at startup instead of in production.
