# 024 Idempotency Keys End to End

Amends [002](002-idempotency-strategy.md) and [015](015-transactional-outbox.md).

## Context

A reviewer's point: idempotency checks are table stakes, and they do not prevent double payments unless the
keys are generated and reused correctly everywhere. A check on the server is only as good as three things
around it:

1. **who generates the key, and when**: a client that makes a new key for every attempt defeats the check;
2. **what "the same request" means**: a fingerprint that compares raw bytes rejects honest retries, and one that
   compares too little lets a different request replay someone else's result;
3. **how long a key is remembered**: on our side, and on the provider's side for the calls we make.

So we audited every path a key travels, wrote the rules down, and gave each rule a test.

## The audit

| Path | Key | Generated by, when | Scope | "Same request" means | Remembered for | Proof |
|---|---|---|---|---|---|---|
| Merchant creates a payment | `Idempotency-Key` header, required | The client, once per checkout, before the first attempt | merchant + payment creation (unique constraint) | same reference, amount by value, currency (stored canonical fingerprint) | as long as the payment exists | `PaymentIntentIdempotencyTest`, `IdempotencyKeyRulesTest` |
| Merchant or operator requests a refund | `Idempotency-Key` header, required | The client, once per refund | payment + refund creation (unique constraint) | same payment, amount by value, reason (stored fingerprint) | as long as the refund exists | `RefundTest`, `IdempotencyKeyRulesTest.shouldScopeRefundKeysToTheirPayment` |

## Decisions

### 1. Clients generate the key once per business operation, and we document how

The full client contract is in [docs/idempotency-keys.md](../idempotency-keys.md). In short: generate the key
before the first attempt, store it with the order, reuse it on every retry (including after a restart), never
derive it from time, attempt numbers or request ids, and retry with the identical request.

### 2. "The same request" is a canonical fingerprint, not raw bytes

- Payments and refunds store a fingerprint of their **business fields** (`RequestFingerprint.of`). Fields are
  sorted and length-prefixed; amounts compare by value (`50000` equals `50000.00`). A null field is left out,
  so adding an optional field later does not change the fingerprint of anything stored before it.
- Operator calls are fingerprinted from the method, the path, the **sorted** query parameters and the
  **canonical JSON** body (keys sorted, whitespace dropped, numbers by value). A body that is not JSON, such as
  a bank statement file, is hashed byte for byte.
- The operation is always part of the fingerprint, so a key reused for a different operation is refused (422)
  instead of replaying the first operation's response or executing the second.
- Per-attempt data (request ids, headers) is not part of the fingerprint.

Before this change the filter hashed raw bytes, so a client that re-serialized a retry (different key order,
`1000.00` for `1000`) got a 422 for an honest retry. `IdempotencyKeyRulesTest` covers it.

### 3. Expiry follows what a late retry would cost

- Payment and refund keys **never expire**: they are part of the record. A retry 30 days later still returns the
  same payment, because creating a second one would charge the customer twice.
- Stored operator responses expire after **24 hours**. An operator tool retrying after that executes the action
  again, which is safe because every operator action re-checks its preconditions (a second settlement run finds
  nothing left to settle).
- A request that failed validation, hit a retryable conflict or a server error is not stored: the key stays free.

### 4. Outbound keys are derived once, and never resent past the provider's memory

- The key is part of the outbox command, written with the business change, unique in the database.
- Dispatch is committed before the call leaves. A worker that dies after the provider acted leaves a dispatched
  command whose lease expires; the next worker asks the provider about **the same key** before sending, finds
  the result, and records it once. `OutboundIdempotencyKeyTest` produces a real crash (the worker's thread dies
  right after the provider answered) and checks the provider's own request log: one key, applied once.
- Providers forget keys (commonly after 24 hours). After that, "I do not know this key" means either "never
  received" or "forgot", and a resend would be a new refund. So a command first dispatched longer ago than
  `payflow.provider.key-resend-window` (23 hours, one hour inside the provider's 24) is **only looked up, never
  resent**; if the provider no longer knows the key, the command is escalated for a person to check the
  provider's records for that transaction.

## Alternatives considered

- **Key per attempt, deduplicate on the request body.** Two customers can legitimately buy the same thing for the
  same amount in the same second; body equality is not identity.
- **Keys generated by the server.** Moves the problem: the client still needs an identifier it can reuse across a
  lost response, which is exactly what a client-generated key is.
- **Expire payment keys after 24 hours like operator keys.** Simpler storage, but a retry from a client that was
  offline for a day would create a second payment.
- **Resend outbound calls under a new key when the old one is unknown.** Correct only if the provider never
  received the first call, which is the one thing we cannot know.

## Consequences

Every path that can move money has a key that is generated once, scoped to one operation, compared by meaning,
and remembered at least as long as a retry can arrive. The mutation check for this ADR: generating the outbound
key per attempt makes `OutboundIdempotencyKeyTest` fail (the provider refunds twice), and so does removing the
resend window.
